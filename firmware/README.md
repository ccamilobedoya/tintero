# firmware

[Leer en español](README.es.md)

ESP32 firmware (C++, PlatformIO). The project owner writes it; agents only help if asked (ADR-0013, in Spanish). This folder is the master copy of the firmware.

## Build and flash

You need [PlatformIO](https://platformio.org/) (the `pio` command line is enough), an ESP32 DevKit with the GDEY075T7 panel and the DESPI-C02 adapter, and your own PKI (`npm run pki -- init`, `server` and `device`; see the certificates guide). All the firmware code is in English; this guide is in English too (its Spanish pair is `README.es.md`).

1. **Wi-Fi.** Copy the template and write your 2.4 GHz network (git ignores the file):
   ```bash
   cp firmware/include/secrets.h.example firmware/include/secrets.h
   ```
2. **This display's certificates.** Generate `firmware/include/tintero_certs.h` with the server name, the display id (`p1`), the CA, and the key and certificate **of that display only** (one display per file: each device carries only its own key):
   ```bash
   npm run pki -- firmware /path/to/pki --host tintero.example.ts.net p1
   ```
   The file gets mode 600, git ignores it, and the tool refuses to write a key into a repo file that git does not ignore. It never prints a key.
3. **Build and flash** (with the ESP32 connected over USB):
   ```bash
   cd firmware
   pio run -t upload
   pio device monitor    # optional: the serial monitor at 115200
   ```
   The firmware only uses the constants of that file (`TINTERO_HOST`, `TINTERO_DEVICE_ID`, `TINTERO_CA_PEM`, `TINTERO_DEVICE_CERT_PEM`, `TINTERO_DEVICE_KEY_PEM`); the server name is in no other file of the repo. For another display, generate the file again with its `pN` and flash.
4. **Authorize the display.** The `<fingerprint> pN` line that `npm run pki -- device` prints must be in the server's device list; otherwise every request gets an empty 404.

The wiring of the panel and of the two buttons (Move on GPIO32 and Accept on GPIO33, each between its pin and 3V3, with the internal *pull-down*) is in `src/panel.cpp` and `src/buttons.cpp`.

## Device security

- **Server validation.** The firmware validates the server **only** against the Tintero CA (`setCACert`): it never turns certificate validation off or uses the public CAs, and every request has timeouts and size limits before reading (section 3).
- **Keys stay readable in *flash*.** Until flash encryption exists (L6), whoever steals the device can read that display's key. That is why each device carries **only its own key**: stealing one does not compromise another.
- **Revoking a display.** Remove its line from the server's device list and restart the server: from then on that display gets an empty 404, even if it keeps its keys. To use it again, issue a new certificate with another id.

## What the ESP32 needs to talk to Tintero

This guide has no real data: the public name, the paths and each display's keys live outside the repo (ADR-0023, in Spanish).

### 1. The display's files (generated by `npm run pki`, F-004/F-012)
- `ca.crt`: Tintero's private CA. The ESP32 trusts **only** it (not the public CAs).
- `pN.crt` and `pN.key`: that display's certificate and key (ECDSA P-256, PEM). The key **never leaves the ESP32** (later, flash encryption, L6).
- The display's `<fingerprint> pN` line must be in the server's device list; otherwise every request gets an empty 404.

With Arduino (`WiFiClientSecure`): `setCACert(ca)`, `setCertificate(crt)`, `setPrivateKey(key)`. With ESP-IDF (`esp_http_client`): `cert_pem`, `client_cert_pem`, `client_key_pem`. This firmware receives the three, already as text, in `include/tintero_certs.h` (see *Build and flash*).

### 2. Before TLS: the time
The server certificate is validated against dates. Without a clock (the ESP32 boots in 1970) the TLS handshake fails. Sync over SNTP **before** connecting (or keep the last good time in the ESP32's RTC between wake-ups).

### 3. Connection
- `https://<public-name>/` on port **443**. The name (SNI) must be the one in the server certificate.
- **One request at a time** (never in parallel); the connection may be reused within a wake-up.
- **Timeouts on every request** (connect and read; e.g. 10 s and 20 s): if the server does not answer, sleep and try again on the next wake-up.
- **Limits before reading** (external input): reject a `Content-Length` larger than expected (index ≤ 2048 bytes, zones ≤ 4096, image = the index's `bytes`) and clamp `next_wake_s` to 30–86 400 s.

### 4. Headers on **every** request
| Header | Value |
|--------|-------|
| `Tintero-Protocol` | `1` |
| `Tintero-Firmware` | text, 1–32 characters (e.g. `esp32-0.1`) |
| `Tintero-Power` | `battery` or `usb` |
| `Tintero-Formats` | `raw1` |
| `Tintero-Panel` | `w=800,h=480,dpi=124,depth=1` (GDEY075T7) |
| `Tintero-Battery-mV`, `Tintero-RSSI` | optional |
| `Tintero-View` | optional: the id of the view the device shows now (see *Focus and actions*) |

### 5. One wake-up
1. `GET /api/v1/index` → `current`, `views[]` (with `hash`, `bytes`, `crc32`), `panel`, `next_wake_s` (it changes with `Tintero-Power`: 600 with `usb`, 1800 with `battery`, by default).
2. If the response's `panel` is not the one declared, show nothing new and come back in `next_wake_s`.
3. For each view whose `hash` changed (starting with `current`): `GET /api/v1/views/{id}/image?h={hash}` and `GET /api/v1/views/{id}/zones?h={hash}`. Check that the image has **exactly** `bytes` (48 000 on the current panel) and its **CRC-32** (zlib's) before storing or showing it.
4. Show `current`; the ESP32 draws the focus (ring) with a partial refresh over the zones (ADR-0006, see *Focus and actions*). If `full_refresh` is `true`, that image is shown with the slow full refresh.
5. The actions taken (also offline) go together in `POST /api/v1/actions` (1–8, each with a unique `id`: the server ignores repeats).
6. Optional: `POST /api/v1/log` with short notices.
7. Sleep `next_wake_s` seconds.

### 6. The `raw1` format
`ceil(width / 8) × height` bytes; rows from top to bottom, pixels from left to right, **most significant bit first**, **1 = black**. If the panel controller uses 1 = white, invert the bytes when sending them.

### 7. Buttons (ADR-0005)
- **Move:** short = next zone (in the order of `zones`); long = next view (in the order of `views`).
- **Accept:** short = the zone's action (`toggle` checks/unchecks, `open` opens the detail); long = go back (in a detail) or refresh now (in a view).

### 8. Responses to handle
| Response | What to do |
|----------|------------|
| 404 with no body | the display is not authorized (or its certificate is missing): check keys and the device list |
| 409 `stale_view` / `stale_zone` | ask for the index again |
| 429 `too_many` / 503 `busy` | wait `Retry-After` seconds and retry |
| 304 | the image did not change (with `If-None-Match`) |
| TLS failure | check the time, `ca.crt` and the name |

### 9. Focus and actions (F-008, ADR-0048 to ADR-0050)
What the device does; the server already delivers the zones aligned and with the blank band.

- **Byte-aligned zones:** each zone's `x` and `w` are multiples of 8, so a zone's partial window is exactly the zone (no split bytes). `validateZones` reports `unaligned` otherwise.
- **The dotted ring.** The zones response carries `focus: { ring, pad, dash }` (at 124 dpi: 3, 6 and 8). The zone's pixels closer than `ring` to its edge are **inverted**; with `dash > 0`, a pixel of the **top or bottom** strip is inverted only if `floor((x − zone.x) / dash)` is even, and one of the **left or right** strip (outside the top and bottom ones) only if `floor((y − zone.y) / dash)` is even. With `dash = 0` the ring is solid. Inside each zone there is a **blank** band of `pad` px (≥ `ring`): the ring never touches content, and removing it is inverting again.
- **States:**
  - *no focus*: on wake-up and when changing view; no zone has a border.
  - *focus*: dotted ring on the zone. **Short Move** = next zone (the first time, zone 1).
  - *sending*: on releasing **Accept**, a **solid** ring by partial refresh and `POST /api/v1/actions`.
  - *applied*: the response carries `index_changed: true` → `GET /api/v1/index` on the same connection (the server waits up to 2 s for the drawing; on `503 busy` wait `Retry-After` and retry **once**), download the new image and show it with **a single fast full refresh**, with the ring already on the zone with the **same id** (the checked task moves to *Done today* and the focus follows it; undoing is another Accept) or, if it no longer exists, on the zone at the **same index** (the last one if there are fewer).
  - *discarded*: `stale` → take the action out of the queue and ask for the index; `duplicate` → take it out of the queue.
  - *offline*: the dotted ring returns and the action stays in the queue (up to 8), with no optimistic mark (ADR-0025).
- **Cleanup.** A fast full refresh when idle (about 30 s, removing the focus) and after a cap of partial refreshes measured on the panel (to start, 10).
- **`full_refresh`.** `true` = the **next** image shown uses the **slow** full refresh. The server sets it on each display's first `index` of the day.
- **`Tintero-View`.** Send on every request the id of the view being shown (also after a view change with a long Move, which the server does not see). The server draws that view first and returns it as `current`; if it does not know it, it ignores it. A value that does not match `^[a-z0-9_-]{1,16}$` gets `400 invalid_request`.
- **Type and strokes.** With the fast refresh, 1 px strokes look faint: the theme uses strokes of at least 2 px. The `calibracion` view (`config/calibracion.views.example.json`) lets you decide on the panel the stroke widths and the detail type (ADR-0049).

### 10. Testing without the display
- `npm run emulator -- --server <url> --ca ca.crt --cert pN.crt --key pN.key --wakes 1` behaves like the ESP32 and leaves in a folder what the panel would show. It is the behavior reference.
- `npm run contract:mock`: a simulator with the contract's example responses.
- All the detail: `contract/openapi/v1.json`, `contract/schema/v1/` and `docs/fichas/F-001-contrato-protocolo.md` (in Spanish).
